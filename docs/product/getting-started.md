# Getting started

Choose one starting point:

- **New app:** In the project folder, give your coding agent the new-project prompt on [openprojectroom.com](https://openprojectroom.com/#get-started). It asks for the first useful release, initializes Git and the official GitHub Spec Kit workflow, and creates `.projectroom/project.yaml` alongside real code and commands.
- **Existing repository:** In the repository folder, give your current coding agent the existing-project prompt from the same page. It reads source entry points and follows wrappers to find services, HTTP APIs, MCP servers, tools, tests and data sources even when no client configuration lists them. It reports file-backed findings and uncertainties and waits for your reply, then creates or updates `.projectroom/project.yaml` without moving the specifications. You can also open the folder in Project Room first and use the project-specific prompt in its setup dialog.

In both cases, wait for the agent's handoff: exact folder, configured findings, uncertainties, and the first service, test and data source to check. Open that folder in Project Room. If it was already open, select **Refresh analysis** in Onboarding. Then inspect the configured entries and run commands deliberately.

For a first real run, choose **Try working example** from the Overview or Projects menu. Project Room copies it into `~/Documents/Project Room Examples/hello-workspace` and opens it. Node.js 20+ is needed for its service and tests. Start its Notes web service manually, run the endpoint tests, inspect the JSON storage, and open the linked Spec Kit feature. The Blackbox Agent B packaged demo uses simulated results.

Open this repository in the Project Room desktop app. Project Room reads `.projectroom/project.yaml` and opens the Overview.

Onboarding distinguishes detected project sections, configured entries and hands-on verification. Undetected optional integrations do not lower setup progress. Green **Configured** states come from the project YAML and repository files. The optional **Mark as verified** buttons stay on this Mac per project; use them after actually opening the map, running a service or test, or inspecting a data source. The read-only review checks paths, commands and missing environment names without running project commands. **Refresh analysis** rescans the repository after an agent changes the files. The advanced automatic setup writes only a minimal YAML from clear repository evidence; it does not create placeholder vision or documentation files.

The left navigation follows the product workflow:

The expanded sidebar shows counts for product content and each Run & Verify collection. These are configured entries (or discovered repository files for Requirements and Documentation), not a count of running services or passed tests. Environment counts variable names without showing their values.

- **Overview** summarizes the workspace; **Project Map** shows components and connections. Switch between Map, List and Source. Source displays the exact `.projectroom/project.yaml` file read from the open repository, or the packaged YAML in the web demo. Add components from the map toolbar. Open **Files** for application source files.
- **Product** contains Backlog, Requirements and Documentation by default. Enable Vision, Roadmap and North Star under Settings → Preferences → Additional views when they are useful; the choice is saved in `workspace.additionalViews` in `.projectroom/project.yaml`. **Run & Verify → Environment** shows required variable names and lets each developer set private values on their own Mac. Documentation browses all Markdown files in `product.docsRoot` with the same folder tree and reader layout as Requirements. Vision is a Markdown file; roadmap entries live in `.projectroom/project.yaml`. Backlog saves local Markdown issues in `product.backlogRoot` (default `backlog/`) and shows optional GitHub or Linear source locations. Live synchronization is still planned.

When a repository uses GitHub Spec Kit, Requirements recognizes its feature folders and constitution. Select a feature to see FR/SC IDs, available artifacts, task and checklist progress, links to configured components and tests, and recorded test results. Refresh folders after external edits. A flat specifications folder remains a normal file browser. Add verified links in `views.specifications.links` when a feature should be tied to specific component and test IDs; `PROJECT_ROOM.md` documents the format.
- **Run & Verify** contains Services, MCP Explorer, Test Explorer and Data Explorer. Services can be started and stopped manually. Expand a test suite to inspect detected Node test files and statically named tests inside them, or discover Rust test names on request; run the full suite, one file or one named test and open its recorded output. Node discovery reads source without executing it; dynamic and duplicate names stay at file level unless listed in `tests.cases`. Other runners can list individual commands through `tests.cases` in `.projectroom/project.yaml`. In Data Explorer, click **Inspect source** to list PostgreSQL, MySQL/MariaDB or SQLite tables, or local files. Select an entry for a limited, read-only preview. Set database connection URLs in local Environment values, never in YAML.
- **Activity** shows recorded workspace events, including test runs and agent connections.

The title-bar **Open** menu gives quick access to workspace, product, Run & Verify, and Activity views. It also opens the bottom event panel, which lists recorded workspace events. The file explorer opens beside the navigation on **Files** and closes when you switch to another page. Command-B opens Files or toggles the tree while you are there; Command-J toggles the event panel. Process output is available on the relevant service or command page. The sidebar button beside the macOS window controls expands or collapses the navigation.

Open **Settings** at the bottom of the sidebar for Preferences, Project & Connections, AI & Chat, and Agent Access. Preferences include System, Light and Dark appearance. **Additional views** lets you show **North Star** and **Command-line Tools** when you need them; both are hidden by default. North Star records one product outcome manually and shows its historical plot. Command-line Tools shows a readable manual for real CLI programs declared in the repository. The view switches are shared in `.projectroom/project.yaml`; appearance stays on this computer. Project & Connections stores GitHub and Linear source locations in `.projectroom/project.yaml`; credentials stay outside the repository. **AI & Chat** detects installed Codex CLI and Claude Code, lets you select one, and defaults to read-only inspection. Product Chat then uses the selected CLI with Project Room's MCP tools. Its microphone transcribes locally on macOS; review the text before sending. Agent Access shows the exact skill, schema, current YAML and MCP setup that a coding agent can read.

The desktop app saves product document edits, North Star definitions and manual measurements, roadmap changes and new map components in the repository. Review and commit these files with the code. Commands run only after an explicit click. Output and events are recorded in `.productview/`.

## API Explorer authentication

Open **Run & Verify → API Explorer**, select **Add API**, and choose None, Bearer, API key or OAuth. For Bearer and API key, enter only the variable name in the dialog, then set its value in **Environment**. Choose a header API key when the service supports it; query keys can appear in server logs. For OAuth, enter the provider's authorization and token URLs, a public native-app client ID and optional scopes. Register `http://127.0.0.1:48271/oauth/callback` with the provider, then click **Sign in with OAuth** on the API. The browser handles consent; Project Room stores access and refresh tokens encrypted on this Mac. **Sign in again** renews authorization, and **Forget sign-in** deletes local tokens. Requests still run only when you click **Send**. OAuth providers that require a client secret or a different callback cannot yet use this flow.

## MCP Explorer

Open **Run & Verify → MCP Explorer** to see project registrations from `.projectroom/project.yaml` separately from client settings in `.mcp.json`, Cursor or VS Code. Client settings can point to external tools; file discovery does not prove that a server belongs to this project. Project Room also includes its own read-only MCP server. Automatic discovery reads configuration only. The optional setup prompt asks your coding agent to inspect source code for servers hidden behind CLI subcommands and other entry points, then register verified ones in YAML after your review. Use **Add MCP server** for a missed server or **Add to project YAML** to register one found in a client config. You can remove YAML entries without deleting source files. Click **Connect** to start a local stdio server or contact an HTTP endpoint; multiple servers may remain connected, and **Disconnect** affects only the selected server. Inspect their advertised tools, resources, templates and prompts. Review a tool’s JSON arguments before **Run tool**. Use **Environment** to set a missing static Bearer variable; remote OAuth servers can open your browser on Connect and return to the local Project Room callback. Tokens stay encrypted on this Mac. The last onboarding step asks you to check these findings.
