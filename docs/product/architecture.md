# Architecture notes

## Desktop releases and updates

The packaged macOS app checks the public `OpenProjectRoom/desktop` GitHub Releases feed after launch and every six hours. A newer version downloads in the background; a bottom banner then offers **Restart to update**. Restarting stops local processes started by Project Room. Development runs never check the feed. The UI is implemented, but a successful signed-to-signed update has not yet been exercised. Release v0.9.69 was signed with Developer ID Application, notarized by Apple, and verified after downloading its ZIP. The tag-triggered GitHub Actions workflow in `.github/workflows/release-mac.yml` publishes the signed ZIP and `latest-mac.yml` along with the DMG. No legacy install migration is needed before the first signed-to-signed update test.

Windows x64 and ARM64 use the same update UI and GitHub release, with one dual-architecture signed NSIS installer and its own `latest.yml`. The Windows job is gated on `WINDOWS_SIGNING_READY` and runs only after the Mac release exists. Windows process commands use one platform adapter for `.cmd` shims and process-tree termination; a PowerShell/CIM snapshot supplies session-only CPU and resident-memory samples. The first Windows install and update remain unverified until tested on a Windows computer. See [Windows preparation](windows-releases.md).

The Project Map shows runtime resources from `.projectroom/project.yaml`: user-facing applications, backend services, databases, storage and persistent CLI servers. Only connections between these resources are drawn. Specifications, test suites, one-off CLI tasks and issue sources remain in the YAML for their dedicated pages and traceability, but do not appear as runtime nodes. Roadmap items refer to component IDs where their work has an architectural effect. A real CLI can be added as a `commandTool` component; its `cli` metadata becomes a manpage-style manual under Run & Verify. This repository does not register a CLI merely to populate that page.

Overview reuses the Project Map's runtime component and connection filters for a read-only preview. It shows up to six components, prioritizing connected entries when the map is larger, and links to the full map for all components and editing. The preview rearranges visible nodes to fit its small card but never invents a connection or claims a configured database is running.
At compact desktop window widths, Overview retains two content columns while the left navigation is collapsed. The four status summaries stay in one row so service controls and performance remain visible without scrolling past a second summary row. The map SVG scales to the available card width; expanding the navigation or narrowing the window stacks the content again.

Foreground service state follows the process Project Room started. A detached service instead declares start, status and stop command arrays. Its status command returns 0 for running, 1 for stopped and 2 or higher for an error. Project Room checks state after an explicit action and polls a confirmed running stack while the app is open; on project open its state remains unknown until **Check status** is clicked. Closing Project Room leaves detached stacks running. Per-process CPU and memory metrics do not represent detached containers. The onboarding review warns when Compose is present but a service lacks a complete detached lifecycle.

Before starting a service or command tool with `runtime.requires: [docker]`, the desktop checks the active Docker context with `docker info`. A missing CLI, unreachable Engine or timed-out check produces a user-facing error without launching the project command. The source-audit guide instructs agents to trace wrappers and declare Docker only when the selected launch path requires it. This prerequisite check does not infer whether a service is healthy after startup.

The Spec Kit adapter reads existing `.specify/` and `specs/<feature>/` artifacts without rewriting them. Optional `views.specifications.links` in `.projectroom/project.yaml` connect feature or FR IDs to existing component and test IDs. The desktop compares those links with its current process state and recorded test events. It labels missing or stale evidence without claiming that file presence or completed checkboxes prove a release.

The local process collector follows applications and services started by Project Room, sampling their process trees every five seconds with one operating-system process snapshot. It sends CPU and resident-memory points to the renderer and keeps a bounded session-only series in the desktop main process. A new run replaces that service's previous series; switching workspaces clears all series. No metric points are recorded in `.productview/` or sent to an agent. The Overview sums measured foreground processes, while Services plots one selected backend service. It does not inspect detached containers or processes started elsewhere.

The current web prototype is a simulation. The desktop app can open a local repository, start configured services and command tools, run tests, read explicitly configured help output, sample local service CPU and memory, and record activity in `.productview/`. Environment variable names are shared in YAML; values are read from the ignored project `.env` and injected only into declared local commands started from the desktop app. Project Room masks known values in command output and excludes `.env` from MCP access. Live issue sync, external telemetry adapters and Railway deployment are planned integrations.

The desktop renderer loads packaged files with a Content Security Policy that permits only packaged scripts and blocks frames and plugins. IPC accepts messages from the main app frame. The history writer rejects symbolic-link folders and files and creates logs without following existing paths. Its `events.jsonl` and `logs/` are ignored in the opened repository by default; deliberately shared evidence still needs human review. Project YAML is limited to 5 MB before parsing to bound accidental or hostile input. CI and release workflows pin third-party actions to reviewed commits and do not persist checkout credentials into build steps.

Build provenance is per executable component. Services and linked CLI tools can declare `build.file`, a repository-relative JSON artifact with `builtAt` (timezone-aware ISO 8601), `revision` and optional `version`. Without an explicit path, the desktop checks `build-info.json` and `dist/build-info.json` under that component's working directory. Only a build pipeline should write `builtAt`, after a successful build. The current Git HEAD is displayed as a separate source revision and cannot substitute for a build timestamp. On manual launch the main process snapshots the metadata and start time, records them in `.productview/events.jsonl`, and keeps the snapshot for the running process even if the file changes. The dashboard, map, Services and CLI Explorer render the same identity. MCP Explorer can read an explicitly declared build file for a local stdio server and separately shows the protocol-reported version and connection time. A remote MCP server has no local build timestamp unless its protocol supplies more data in the future. Missing metadata is reported as unavailable, not guessed from filesystem mtimes.

Product Chat can run the locally installed Codex CLI or Claude Code from the desktop app. Settings → AI & Chat stores the chosen provider and inspect/edit permission mode in app data, separate from the repository. Each request runs in the selected workspace with Project Room's read-only MCP server and the agent's own configured tools. Chat prompts and replies are recorded in `.productview/events.jsonl`; local environment values are not included in the prompt or MCP output. The microphone uses macOS on-device speech recognition and inserts text into the composer before the user sends it.

Personal appearance and sidebar preferences stay local to the app or browser. Project connections are shared metadata in `.projectroom/project.yaml`: GitHub uses `integration.repository`, Linear uses `integration.teamId`, and either may include a display `integration.url`. The Settings UI can edit these locations in a desktop workspace. It does not yet authenticate or fetch issues; credentials must not be committed to the repository.

The Backlog combines repository-backed local issues with Spec Kit features, bug reports and idea assessments. Local issues remain Markdown files in `product.backlogRoot` (default `backlog/`), with stable IDs and frontmatter. An optional `spec` path links one to `specs/<feature>/`, `.specify/bugs/` or `.specify/assessments/`; linked work appears once. Project Room reads Spec Kit artifacts in place and does not copy or edit them. Roadmap is a separate optional product milestone view, not a duplicate list of implementation tasks.

## MCP Explorer

The desktop's immediate MCP inventory reads project client configuration and `workspace.mcpServers`; it does not claim to infer every server from arbitrary source code. The optional setup prompt passes a repository-specific guide to the user's coding agent. That agent must complete the guide's source-audit matrix for product context, Web/Desktop/Mobile applications, backend services, HTTP APIs, MCP servers, CLI tools, tests, data and runtime evidence. It traces wrappers and hidden subcommands, makes a second source pass before reporting absence, and reconciles any existing YAML against source. This catches a local `stdio` MCP server exposed only as a CLI subcommand. The first-phase report separates verified implementations from uncertain candidates, names source evidence, environment variable names and access scope, and waits for review. A server requiring a separate read-only key must not receive an owner credential. Registration does not connect or invoke it; the user tests the server in MCP Explorer deliberately.

The source audit improves setup completeness but is not a universal protocol importer or a runtime test. MCP Explorer supports local `stdio`, Streamable HTTP and legacy SSE with manual connection; custom transports need an adapter. It labels project registrations separately from coding-tool client settings, which can point to external servers. API Explorer uses existing OpenAPI 3.x documents, an explicitly loaded OpenAPI path on a registered API, or manually entered HTTP paths and supports none, Bearer, API key and public-client OAuth; GraphQL, gRPC, multipart uploads, cookie/Basic/mTLS and confidential OAuth clients have no dedicated request flow. CLI Explorer discovers common package, Python, Cargo, Go and executable entry points; unbuilt package targets are visible but cannot be run until built. Individual subcommands and safe arguments still need source review or explicit help. Test Explorer can discover Node and Rust cases in supported forms; other runners need explicit test commands. Data Explorer handles PostgreSQL, MySQL/MariaDB, SQLite and local files, not every database or event stream. Foreground services and explicitly modeled detached lifecycles are operable; the CPU/memory collector does not measure containers after a detached launch. The agent should mark these limits as unsupported or manual rather than fabricate an integration.

## API Explorer

Project-local OpenAPI 3.x files are scanned read-only and listed beside HTTP APIs declared in `workspace.apiSources`. The file remains the source of truth for endpoint paths and summaries; the repository YAML stores only its relative path, clean base URL and public authentication metadata. Alternatively, `specPath` identifies a dynamically served OpenAPI document on the registered API. The user must click **Load OpenAPI**; the main process fetches from that API's origin without redirects or authentication headers, with a timeout and 2 MB limit. An API can be registered without a spec and tested with a manually entered relative path. The main process performs a request only after the user clicks Send, checks that the target stays on the selected origin, blocks redirects, applies a timeout and bounds the response preview. It resolves Bearer and API-key values from the local project `.env`. Public-client OAuth uses PKCE and a loopback callback; access and refresh tokens are encrypted outside the repository with macOS secure storage. Activity records only request metadata, without headers, query values, body or response content. The included Hello Workspace has a matching OpenAPI document for its real health and notes endpoints.

## MCP Explorer

The desktop main process uses the official MCP client SDK to connect to explicitly selected project servers over stdio, Streamable HTTP or legacy SSE. It keeps one client session per connected server, so several can remain connected while the user switches between them. Read-only discovery scans project-local MCP configuration and shared `workspace.mcpServers`; it does not launch anything. Add, link and remove actions update the YAML array atomically after schema validation; linked entries record the discovered source ID. The renderer gets safe server metadata, capabilities, schemas and user-requested results over IPC. Connect, disconnect and invocation metadata goes to `.productview/events.jsonl`; arguments and responses remain in memory. YAML declares only static variable names or public OAuth client metadata. Static values come from the ignored project `.env`; SDK-managed OAuth credentials are encrypted locally and scoped to the workspace and endpoint. The built-in Project Room MCP server serves coding agents and is hidden from the project MCP Explorer.
